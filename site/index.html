The problem

The checks exist. The assessment doesn't.

Data teams already run dbt tests, a Great Expectations suite here, a Soda scan there. Each covers one engine, writes its own report, and gives a score, if any, with no sense of how sure it is.

Coverage stops at hand-written tests. Every check someone has to write is a check that usually isn't written. The 1,200 tables nobody wrote tests for are where the problems live.

One engine at a time. Deequ needs Spark, Elementary needs dbt models, Pandera needs DataFrames, TestGen needs a SQL warehouse. Nothing reads Postgres and the Parquet files on S3 in one pass.

Scores without error bars. A score from a 1 % sample looks as certain as one from every row. Nobody can tell a real drop from sampling noise.

The open tools closed up. Soda Core moved to the Elastic License, GX Cloud shut down, and anomaly detection sits behind cloud paywalls. Self-hosting the good parts got harder in 2026.

How it works

Profile it. Check it. Score it. Explain it.

One loop for every table in the store. Each run adds to a history, so the checks, the thresholds and the scores get sharper the longer Sahifa watches.

  1. 1

    Profile every column

    Types, null shares, distinct counts, patterns, ranges and keys, computed inside your database or on the files where they lie. Roles and semantic types (IBAN, email, VAT ID) are inferred.

  2. 2

    Checks written for you

    Rules start active, baselines learned from your data start as proposals. You lock what you trust; Sahifa never re-generates a locked check.

  3. 3

    Score with an error bar

    A score per ISO/IEC 25012 dimension for every column, table and the store, with a 95 % interval from the rows actually read.

  4. 4

    Explain and propose

    Every finding names the count, examples (masked when personal), the SQL that found them and a next step. Sahifa never writes to your data.

Architecture

Checks run where the data lives.

A Python core turns the catalogue into SQL and pushes it down: one profile query and one check query per table, on a reproducible sample. DuckDB reads files and object storage. Results, history and findings live in Postgres. Runs on one server with docker compose, or on CapRover.

Boundaries

What Sahifa deliberately is not.

Not a cleaning tool. It never writes to a source. Fixes are proposals you apply in your own pipeline.
Not a copy of your data. It keeps profiles, counts and at most five masked examples per finding, never the tables.
Not an AI that judges your data. Models may propose rules; a person approves them and the engine runs them deterministically.
Not a SaaS or an open-core teaser. Every feature is in the Apache-2.0 build, for any number of users and connections.

The name

Why the name

The Ṣaḥīfa of Medina was the written charter the Prophet ﷺ agreed with the people of the city. It set down in writing what each party could expect of the others. A data contract does the same for a table.

The Sīra also tells of another ṣaḥīfa: the boycott document hung in the Kaaba, found eaten by termites except for the name of Allah. Records decay unless someone looks after them. Sahifa does the looking.
